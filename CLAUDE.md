# Termy Code

Desktop client for ACP coding agents (Claude Code, Codex, Cursor, plus Grok, Gemini CLI as "Antigravity", and OpenCode). Tauri 2 + React 19 + Effect 4, package manager is Bun.

## Commands

```sh
bun install
bun tauri dev                                   # run the app (starts Vite on :1420 via beforeDevCommand)
bun tauri build                                 # release bundle
bun run build                                   # tsc typecheck + vite build of the frontend only
bunx tsc --noEmit                               # typecheck only
cargo check --manifest-path src-tauri/Cargo.toml
```

There is no frontend test suite or linter. Rust has unit tests (`cargo test --manifest-path src-tauri/Cargo.toml`), including daemon tests that drive a fake ACP agent through `python3`. `src/routeTree.gen.ts` is generated by the TanStack Router Vite plugin; don't edit it by hand.

`alacritty_terminal` provides the native PTY transport through `src-tauri/src/pty.rs`: raw output for xterm.js, per-command environment, bounded input, resize, process termination and exit status. Cargo fetches it from crates.io; no sibling repository is required. Interactive shells use the user’s login shell; terminal preferences live in the app settings.

## Architecture

- `src-tauri/`: Rust. Agents and shells run in a background daemon (`daemon/`): the same binary started with `--daemon`, which outlives the app like a terminal multiplexer. It proxies each agent's ACP stdio (renumbering the window's request ids, answering `fs/*` and `terminal/*` itself, logging notifications to disk, holding permission prompts until a window attaches) in `daemon/agents.rs`, and keeps shells with scrollback on Alacritty's PTY in `daemon/shells.rs`. The app connects over a Unix socket (`daemon_client.rs`, paths in `paths.rs`) and exposes `daemon_request` plus `daemon://event` to the webview. The rest runs in the app: ACP `terminal/*` commands with sanitized text output (`agent_terminal.rs`, used by the daemon), SQLite projects and threads (`db.rs`), file reads and image attachments (`workspace.rs`), `@`/`$` mention lists (`mentions.rs`), and the login-shell `PATH` (`shell_env.rs`). Every command is registered in `lib.rs`.
- `src/services/`: Effect services. `Workspace` owns all app state (a `SubscriptionRef`) and agent session lifecycles; `AcpClient` wraps the ACP SDK; `Daemon` fronts the background daemon; `AgentHost` turns a daemon agent into an ACP stream (spawn, or attach with log replay); `TerminalHost` opens or reattaches daemon shells by key; `Database` fronts the SQLite commands; `Tauri` is the single Effect boundary over `invoke`/`listen`/dialogs.
- `src/domain/`: pure types and reducers (session timeline, tool stacks, diffs, Cursor's `cursor/*` ACP extensions). Agent launch specs live in `domain/agents.ts`.
- `src/routes/`: TanStack Router file routes. UI primitives come from shadcn on Base UI (`src/components/ui`); the Notra registry provides shimmer and the step slider.

### How an agent session flows

1. The daemon's `agent.spawn` starts the process, keyed by thread id, and `agent.attach` streams its messages as `agent.entry` (numbered, logged notifications) and `agent.message` (requests and responses) events. `AgentHost` turns those into a `ReadableStream`/`WritableStream` pair. Closing its `Scope` only detaches; `AgentHost.kill` stops the agent (closing a tab or deleting a thread).
2. `AcpClient.connect` builds an ACP `ClientSideConnection` over that stream, skipping `initialize` when attaching to an agent that already did it. The client side of ACP (`fs/*`, `terminal/*`) is answered by the daemon and never reaches the webview; permission prompts and `cursor/*` extensions are delegated to handlers supplied by `Workspace`.
3. `Workspace.ensureConnected` keeps one `Live` handle per thread (a `Scope`, a `ready` Deferred shared by concurrent callers, the pending user request). `establish` resumes, loads (replaying history, ignored while `replaying`), natively forks, or creates a new ACP session, in that order of preference.
4. Session updates go through `applyUpdate` in `domain/session.ts` into the thread's `Session` inside the `SubscriptionRef`. Requests that need user input (`Permission`, `Question`, `PlanApproval`) are set as `session.request` and block on a Deferred until the UI answers.
5. Threads are persisted once they contain a user message: the whole `items` timeline is stored as a JSON column in SQLite (search is a `LIKE` over title and items), with `log_seq`, the daemon log entry it's saved up to (acked so the daemon can trim). A turn ends on the daemon's `_termy/turn_end` notification, not the `session/prompt` response, so turns that finish with no window open still end. On launch, `Workspace` reattaches threads whose agents are still running and replays their log after `log_seq`. Open tabs, panel shells, the last page and each agent's last mode are kept in `localStorage`.

The daemon is replaced automatically when it's idle and from another build; with work running it's kept (Settings shows it as stale and can restart it). `TERMY_DATA_DIR` points both processes at another data folder, e.g. for tests.

### React ↔ Effect

`src/lib/runtime.tsx` holds the `ManagedRuntime`. Components read state with `useWorkspaceState(select)` (a `useSyncExternalStore` over the `SubscriptionRef`; `select` must return stable references) and run actions with `useRun()`, which turns failures into toasts. Errors reaching the UI must carry a user-facing `message`.

# Learning more about Effect

This repository uses the Effect Typescript library.

Before writing any Effect code, first read `node_modules/effect/AGENTS.md`
**completely**, and follow the links in the file when required.

If you need to learn more about particular Effect apis and concepts that the
guide doesn't cover, search through the source code in `node_modules/effect/src`.
